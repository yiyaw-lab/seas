## 8. Phase G — tripwire / proactive alerts (built today)
Flips Argo from reactive (you ask, it answers) to **proactive** (it watches, it
tells you). `src/argo_watch.py`, run as a batch job on a cron, NOT in the webhook
(so it can never slow chat).

**The logic, step by step:**
1. **Fetch** — pull recent items (PER_FEED=10 each) from every feed in
   `fetch_signals.FEEDS` via `fetch_feed`. (To make alerts linkable, the feed
   parser was extended to capture each item's `link`/`id`, which it previously
   dropped.)
2. **Identity** — each item gets a stable id (`_item_id`): its link, falling back
   to title, lowercased. This is what dedup keys on.
3. **Dedup** — load the seen-store (`data/argo_seen.json`, a list of ids); keep
   only items whose id is NOT already seen. This is what prevents repeat-spam: an
   item is alerted at most once, ever.
4. **LLM judge** — the new items go to one model call (the chat model: Claude if
   keyed, gpt-4o fallback) asking *"which of these would a frontier builder want
   to know TODAY?"* — real launches / new models / tools / capability jumps, and
   explicitly DROP routine papers, incremental research, and noise. "Most items
   should be dropped." It returns at most MAX_ALERTS kept items, each as a sharp
   one-liner + the link, or the literal `NONE`.
5. **Parse + cap** — the judge's output is split into `<sentence>\n<link>` blocks,
   capped at MAX_ALERTS=3.
6. **Send** — each kept alert is sent via `send_telegram.send_message` (run
   through `_clean_reply` so it stays plain-text / no markdown).
7. **Record** — ALL new items (alerted or not) are appended to the seen-store and
   committed by the workflow, so the next run won't reconsider them. Store is
   bounded (SEEN_CAP=2000).

Why each guard matters: **dedup** stops repeats, the **LLM judge** is the
signal/noise filter (a dumb "alert on anything new" would fire ~50x/day), and the
**cap** bounds the worst case even if the judge over-keeps.

- `.github/workflows/argo-watch.yml` — cron ~3×/day (14/19/00 UTC), commits the
  seen-store, concurrency-guarded so overlapping runs can't double-send.
- **Verified (dry run, `--no-send`):** from 72 new items it kept exactly 3
  high-signal alerts (Nous self-improving agent, NVIDIA Cosmos 3, GitHub Copilot
  SDK GA) and dropped the routine arXiv papers; dedup confirmed (72 new → 0 on
  rerun with those ids seen); cap honored; dry-run left the seen-store untouched.
- **First live CI run FAILED** on stale repo secrets (ANTHROPIC_API_KEY not a
  repo secret → fell back to OpenAI → the stored OPENAI_API_KEY was the *old
  revoked* key → 401). Code is correct; fix is to set/refresh GitHub repo secrets

## 8b. Phase C — repo/code read (built today)
Two tools added to the MCP server (`src/argo_mcp_server.py`) so Argo can reason
about actual code, not just trending titles:
- `github_list(repo, path)` — list files/dirs in an approved repo.
- `github_read_file(repo, path)` — read a file's contents (capped at
  MAX_FETCH_CHARS).

**Logic / guards:**
- **Repo allowlist** (`GITHUB_REPO_ALLOWLIST`, default `yiyaw-lab/seas`; `*`
  allows any public repo) — non-approved repos are refused, mirroring the
  web_fetch host allowlist.
- **Auth** via `GITHUB_TOKEN`/`GH_TOKEN` when present (REQUIRED for private repos
  like seas; optional for public). Calls the GitHub REST contents API; a 404 on a
  private repo returns a "needs GITHUB_TOKEN" hint.
- Read-only; output capped.
- **Verified:** listed `src/`, read `requirements.txt`, refused `torvalds/linux`
  (not on the allowlist). Prompt updated to tell Argo it can read code.
- For live chat use, `GITHUB_TOKEN` must be set in Railway (else private-repo
  reads 404).
