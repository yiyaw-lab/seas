# SEAS + Argo

This repository hosts two complementary systems for working at the frontier of AI:

- **SEAS** — a **research engine**. It turns frontier signals into knowledge.
  It asks: *"What is true?"*
- **Argo** — a **decision engine** (evolving into an **insight engine**). It turns
  that knowledge into action. It asks: *"What should I do next?"* — and,
  increasingly, *"What is everyone missing?"*

SEAS generates understanding. Argo generates motion.

```
        ┌──────────────────────────────┐        ┌──────────────────────────────┐
        │  SEAS — research engine      │        │  Argo — decision/insight     │
        │  "What is true?"             │ ─────► │  "What should I do next?"    │
        │  → findings & theories       │        │  → one project worth building │
        └──────────────────────────────┘        └──────────────────────────────┘
```

---

## SEAS — Frontier Research Engine

SEAS transforms frontier signals into artifact-producing experiments, findings,
and theories. Its purpose is to **generate knowledge**.

### North Star

```
Signal → Opportunity → Experiment → Finding → Theory
```

Each stage converts the one before it into something more durable: a change in
the world becomes a framed opening, an opening becomes a test you can build, a
test produces evidence, and evidence accumulates into a generalized claim.

### Core Concepts

| Concept | Definition |
|---|---|
| **Signal** | Something that changed in the world. |
| **Opportunity** | A frontier opening that can be converted into an artifact-producing experiment capable of generating capability gain, public value, and reusable insight. |
| **Experiment** | A structured test or build designed to investigate an opportunity. |
| **Finding** | Evidence or insight generated by an experiment. |
| **Theory** | A generalized claim derived from one or more findings. |

### The live pipeline

The runnable SEAS loop is orchestrated by `src/seas.py`:

```
inbox/signals.md
   │  (process_inbox.py)
   ▼
data/signals.json ──► opportunities.py ──► data/opportunities.json ──► main.py ──► runs/<date>-experiment.md
                          (score.py)                                   (experiment.py)
```

Run it:

```bash
python src/seas.py
```

This prints a weekly status, ranks opportunities from scored signals, and writes
an experiment card to `runs/`.

> **Note on history.** SEAS went through earlier capability-centered designs.
> Docs describing those are retained but marked `SUPERSEDED`, and the obsolete
> machinery is slated to move under `archive/` (see
> [PHASE_1_PLAN.md](PHASE_1_PLAN.md)). The architecture above is the current
> source of truth. A full inventory lives in [AUDIT.md](AUDIT.md).

## Argo — Frontier Scout

Argo consumes SEAS's knowledge and converts it into a single thing worth doing.
Its purpose is to **generate action**. Argo is **not** a chatbot, a news bot, a
task manager, or a recommendation list — it is a point of view.

### Loop

```
Observe → Interpret → Select → Recommend → Reflect
```

Argo places **one Bet per week** (not a ranked list), delivered like a frontier
scout texting you something they found — leading with the insight, presenting the
project as a bet. The product is **one project, not a report.**

### Core objects

| Object | Owner | Meaning |
|---|---|---|
| **Bet** | Argo | The one project Argo wagers you should build this week (confidence × upside). Argo's core object. |
| **Energy** | Argo | A 1–10 score — *"how much do you want to build this?"* — Argo's optimization target. |
| **Project** | Argo | A Bet you accepted and are building. |
| **Artifact** | Argo | The public output (repo / post / demo). The thing that compounds. |

SEAS owns Signal/Opportunity/Finding/Theory; Argo owns Bet/Project/Artifact/Review.

### Argo V1 — Weekly Bet + Energy (live)

V1 proves delivery, weekly bets, and energy tracking. It picks one Bet from a
curated frontier pool, prints it in scout voice, then asks for your Energy Score
and logs it to `data/argo_bets.json`.

```bash
python src/argo.py
```

The predicted energy is stored internally but **never shown**, to avoid anchoring
your reported energy. The energy question is asked as a separate moment, after
the bet is delivered.

### Argo V2 — Insight Engine (design / experiment)

A redesign in progress: Argo should generate **original insight first** and a bet
second. The strongest messages are valuable because of the *observation* that
precedes the project, not the project itself.

```
Signal → Observation → Insight → Bet → Energy → Artifact
```

V2 evolves *beside* V1 without replacing it. See:
- [ARGO_ARCHITECTURE.md](ARGO_ARCHITECTURE.md) — Argo V1 (decision engine), frozen.
- [ARGO_V2.md](ARGO_V2.md) — Argo V2 (insight engine), approved design.
- [ARGO_V2_MIGRATION.md](ARGO_V2_MIGRATION.md) — the smallest path from V1 to V2.

### Argo as an agent (live)

Argo is a two-way, always-on Telegram agent. It runs as a webhook on Railway
(`src/argo_webhook.py`), thinks with Claude (model-routed: Sonnet for routine
turns, Opus for high-stakes ones; gpt-4o fallback), and has tools.

- **Two-way chat** — text the bot, it replies in a frontier-scout voice with
  persistent memory (append-only log on a Railway volume). A bare `1-10` reply
  records a project's energy score.
- **Live web access (tool)** — `src/argo_mcp_server.py` is an MCP server exposing
  `web_fetch` over an **approved-host allowlist** (arXiv, GitHub, Hugging Face,
  OpenAI, Anthropic, Google AI). Claude calls it via the Anthropic MCP connector,
  so Argo reads real current pages/papers instead of guessing. Prefers RSS feeds
  for sites that block scraping.
- **Tripwire (proactive alerts)** — `src/argo_watch.py` runs on a cron
  (`.github/workflows/argo-watch.yml`, ~3×/day): it fetches the frontier feeds,
  dedups against `data/argo_seen.json`, asks an LLM judge *"would a frontier
  builder want to know this today?"*, and texts up to 3 alerts + links for real
  launches/tools/capabilities — dropping routine noise. This flips Argo from
  reactive to proactive.

See [build-log/](build-log/) for the dated build history and
[docs/ARGO_WEBHOOK_SETUP.md](docs/ARGO_WEBHOOK_SETUP.md) / [docs/ARGO_LLM_SETUP.md](docs/ARGO_LLM_SETUP.md)
for setup.

## The Weekly Message + Telegram

The weekly bet is rendered in a frontier-scout voice by a **single formatter**
(`argo.format_bet` in `src/argo.py`). The demo pipeline calls that same formatter
so the Telegram message and Argo's own output can never drift apart.

```bash
python src/seas_demo.py     # writes demo/SEAS_DEMO_REPORT.md + demo/weekly_project_message.md
python src/send_telegram.py # sends demo/weekly_project_message.md via the Telegram Bot API
```

Telegram delivery is a minimal proof of concept (send-only). Setup —
creating the bot, getting your chat id, and adding repo secrets — is documented
in [docs/TELEGRAM_SETUP.md](docs/TELEGRAM_SETUP.md).

## Automation

| Workflow | Schedule | What it does |
|---|---|---|
| `seas-weekly.yml` | Mondays 15:00 UTC | Runs `python src/seas.py` and commits updated `data/` + `runs/`. |
| `seas-friday-telegram.yml` | Fridays (15:00 UTC) | Generates a fresh Argo V2 project and sends it to Telegram. |
| `argo-watch.yml` | ~3×/day (14/19/00 UTC) | Tripwire: fetches frontier feeds, judges new items, texts up to 3 alerts + links, commits the seen-store. |

> GitHub cron is UTC with no daylight-saving awareness; the Friday job lands at
> 08:00 Pacific during PDT and 07:00 during PST. See
> [docs/TELEGRAM_SETUP.md](docs/TELEGRAM_SETUP.md).

## Quick Start

```bash
# SEAS — generate this week's experiment from scored signals
python src/seas.py

# Argo V1 — get this week's bet and record your energy
python src/argo.py

# Preview the weekly scout message (no Telegram needed)
python src/seas_demo.py && cat demo/weekly_project_message.md
```

Requires Python 3.11+. No third-party dependencies — everything uses the standard
library.
