## TL;DR
Argo got the parts the vision was missing. **Rehearse** now sits between SELECT and
the build: when a project is chosen, three adversaries (a red-team critic, a
skeptical user, an ops/failure simulator) attack the bet and an Opus judge issues a
verdict (SHIP / REVISE / KILL) plus a hardened, build-ready blueprint with dated
kill-criteria and concrete first steps — "the factory that argues with itself
before it ships." Underneath that, the codebase grew a spine: a 39-test harness,
structured logging, and a shared-utils layer (paths/store/http/rating/github) that
removed a pile of duplicated json/ssl/path code. And the user's identity was lifted
out of ~30 hardcoded prompt strings into a profile, so the code is multi-user ready.

A notable meta-lesson surfaced and got written into the rules: multiple agents
edited the same files at once, and the harness shows a peer's edits only as
anonymous "file modified" notices. One session burned real effort treating a peer's
refactor as lint noise and trying to strip it out. CLAUDE.md now has a
"Working alongside other agents" section so that doesn't recur.

## 1. Rehearse — the debate/simulation gate (the keystone)
`src/argo_rehearse.py` (new). Until today, the moment a project was SELECTed it
went straight to a kickoff plan — nothing stress-tested the bet first. SEAS+Argo
alone is "generate -> build," which the vision named as closer to the enemy (the
slop factory) than the goal. Rehearse is the gate.

The pipeline, mirroring the SEAS emission-gate pattern (a draft must *earn* its
output):
- **Three adversaries, in parallel** (Sonnet each, via a `ThreadPoolExecutor` so
  wall-clock ~= one call): a red-team critic (why the insight is wrong / done /
  won't matter), a skeptical user (would anyone use, cite, or share it), and an
  ops/failure simulator (what breaks in the build, what the demo looks like when it
  goes wrong).
- **A judge** (Opus) weighs the bet against all three, issues SHIP / REVISE / KILL
  with a robustness rationale, answers each surviving objection, and on SHIP/REVISE
  emits the hardened plan: the sharpened bet, failure scenarios + mitigations,
  **dated, mechanically-checkable kill-criteria** ("if X is not true by YYYY-MM-DD,
  stop"), and concrete BUILD STEPS — everything a coding agent needs to start.
- **A KILL writes no build plan** and routes the bet back into the rate/another
  loop — the gate refusing to bless a weak project, the way a failed SEAS draft
  becomes a probe, not a finding.

Output is a build-ready blueprint at `argo/rehearsals/P-NNN.md` (gitignored —
generated per-rehearsal). Wired into the SELECT gate (rehearse before scaffold,
with a scaffold fallback if it errors) and exposed as the `rehearse_project` MCP
tool. Reuses `argo_observe`'s provider routing + DailyBudget/CircuitBreaker guards;
only the judge escalates to Opus.

Verified live (`--no-send` on P-001): produced a genuine REVISE — reframing a
static-prediction CLI into a record-and-replay accelerator — with conceded
objections, failure mitigations, and dated kill-criteria.

## 2. User profile — de-hardcode the single user
`src/profile.py` + `data/profile.json` (gitignored) + `data/profile.example.json`
(committed template). The user's identity ("Yiya", "she", "a frontier AI builder",
her register/style) was woven through ~30 prompt strings, docstrings, and chat
role labels. It's now one profile object templated into every prompt surface:
`argo_webhook`'s `SYSTEM_PROMPT` became `build_system_prompt(profile)`,
`taste_signals` and `argo_project`'s prompt constants became builder functions, and
the MCP tool docstrings were genericized to "the user."

The behavioral half of the system prompt (tools, self-heal, attribution) is
untouched — only the identity span is templated, so output is **byte-identical**
for the existing user (verified by regression). A swap test (name=Alex/they)
confirmed zero leftover identity; a missing `profile.json` falls back to a built-in
default, so it can't brick the bot. Scope was deliberately a single active user;
the data stores stay global, shaped so per-user partitioning later is additive.
The profile file is gitignored (real user identity shouldn't be public in a
multi-user app); the committed example documents the schema, `.env.example`-style.

## 3. Tripwire — gate on strength, not a count
`src/argo_watch.py`. The tripwire capped alerts at `MAX_ALERTS=3` per run, which
could silently drop the 4th genuinely-important item while a quiet day's low count
came from the bar itself, not the cap. The relevance bar, not a number, is the
lever. The judge now keeps every item a frontier builder would *absolutely want to
know today* with no target count; `ALERT_SAFETY_CAP=8` is a runaway backstop only,
not shown to the judge. A run with 4 must-know items now sends 4.

## 6. Meta: collaborating across parallel agent sessions
`182df3d`. Multiple Claude sessions edited this repo concurrently, but the harness
surfaces a peer's edits only as anonymous "file modified" notices — you can't see
who. One session read a peer's shared-utils refactor as lint noise and spent real
effort trying to un-apply it from "their" files (a soft-reset + temp-file split
detour) before realizing it was legitimate concurrent work. Net outcome was fine
(explicit per-file `git add` kept commits additive, so nothing clobbered), but the
lesson is now a CLAUDE.md "Working alongside other agents" section: assume
unfamiliar edits are a peer's work and build on top, keep commits additive and
per-file, never rewrite history on a shared branch, and reuse the shared-utils
layer instead of re-inlining. Also recorded the `claude-opus-4-8` gotcha — it
rejects the `temperature` param (the API 400s); `chat_with_mcp` now omits it for
those models, which also unbroke the webhook's Opus-escalated chat turns.

## What's next
- **Rehearse on real bets.** It's verified on P-001 in `--no-send`; next is letting
  a live SELECT run it end-to-end on a fresh project and watching the blueprint
  quality + cost (4 model calls/SELECT, judge on Opus).
- **Module size.** `argo_webhook.py` and `argo_mcp_server.py` are still over the
  500-line bar even after the rating/github extractions; the next substantive change
  to either should carve one more cohesive seam.
- **Multi-user, when it's real.** The profile is single-user by design; partitioning
  the data stores by `user_id` + routing delivery per profile is the additive next
  step the abstraction was shaped for — not before there's a second user.
- **Parallel-agent friction.** The CLAUDE.md rules are guidance, not enforcement;
  the harness still won't tell an agent a peer is active. If concurrent sessions
  stay common, separate branches per session (or a lock on hot files) is the real
  fix.
